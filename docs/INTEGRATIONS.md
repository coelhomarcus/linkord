# Third-party integrations

Every external service Linkord talks to, what it is used for, who makes the call (our server or the user's browser), the credentials it needs, and what happens when it is missing or fails. For setup steps see [DEVELOPMENT.md](DEVELOPMENT.md); environment variables are listed in [`.env.example`](../.env.example).

## Overview

| Service | Purpose | Called from | Credentials | Required |
| --- | --- | --- | --- | --- |
| [LiveKit](#livekit) | Voice, video and screen sharing | Server (SDK) and browser | `LIVEKIT_*` | For calls |
| [Resend](#resend) | Account recovery, email-change, two-step login and account-deletion codes, plus the codes that confirm security changes with two-step login on; new sign-in alerts, email-changed, account deletion notices, data export links | Server | `RESEND_*` | For email flows and two-step login |
| [Web Push](#web-push) | Browser push notifications | Server | `PUSH_VAPID_*` | No |
| [KLIPY](#klipy) | GIF picker | Browser | `KLIPY_API_KEY` | No |
| [MyAnimeList](#myanimelist) | Profile Wall widget | Server (background worker; covers through the [media proxy](#media-proxy)) | `MAL_CLIENT_ID` | No |
| [GitHub](#github) | Profile Wall widgets | Server (background worker; avatar through the [media proxy](#media-proxy)) | None | No |
| [IGDB](#igdb) | Game search for the Wall's games widgets | Server (on demand; covers through the [media proxy](#media-proxy)) | `IGDB_CLIENT_ID`, `IGDB_CLIENT_SECRET` | No |
| [Arbitrary websites](#link-previews) | Link preview cards | Server (pages, and their images through the [media proxy](#media-proxy)) | None | Built in |
| [oEmbed providers](#oembed) (YouTube, Vimeo, SoundCloud, Spotify, X, TikTok, Reddit) | Link preview cards for their links | Server | None | Built in |
| [YouTube and Twitch](#embedded-players) | Inline players for pasted links | Browser (players); server (YouTube thumbnails, through the [media proxy](#media-proxy)) | None | Built in |

"Server" means the Node process in `server/`; "browser" means the web client in `web/`. The pictures these services provide (covers, avatars, preview images, favicons, YouTube thumbnails) reach the browser through our own [media proxy](#media-proxy), so they show on networks that block those domains. Apart from that, where a service is called from the browser the server does not proxy the traffic.

Two things are deliberately **not** third-party calls: fonts are bundled with `@fontsource-variable/figtree` (no font CDN), and [webhooks](WEBHOOK.md) are inbound requests from other systems into Linkord, not calls we make.

## LiveKit

Selective forwarding unit (SFU) behind every voice channel and 1:1 call.

- **Code:** [`server/src/integrations/livekit/livekit.ts`](../server/src/integrations/livekit/livekit.ts), plus the `call-token` message in `server/src/realtime/socket.ts`. The browser uses `livekit-client`.
- **Server → LiveKit:** `livekit-server-sdk` signs a short-lived access token per call (`createToken`, lifetime `LIVEKIT_TOKEN_TTL_SECONDS`, default 60; the client connects as soon as it arrives) scoped to one room named `${LIVEKIT_ROOM_NAME}-${conversationId}`. In a voice channel the grant lists only the sources the member's channel permissions allow (`SPEAK`: microphone; `STREAM`: camera, screen share and its audio), so the SFU itself refuses the rest; a DM call allows all of them. When a role, overwrite, channel or ownership change alters those permissions mid-call, `enforceCallPermissions` (`server/src/modules/calls/callPermissions.ts`) calls `updateParticipant` with the new sources (LiveKit unpublishes what is no longer allowed), or removes the member from the call if they lost `CONNECT`. When membership is revoked, `RoomServiceClient` lists and removes the account's participants (`evictFromCall`, three attempts with backoff). Failures are logged and never roll back the database change.
- **Rooms follow the server:** a LiveKit identity is a connection id, and it belongs in a room only while the server has that connection in that call. Whenever a connection stops being in a call (`call-leave`, a move to another call, a revoke, the end of a DM call, its reconnect grace running out), `removeParticipant` takes it out of the room too (`server/src/modules/calls/callRoomSync.ts`, through `setCallLeftHook`). A token cannot be recalled, and LiveKit refreshes it for connected clients, so every 15 s the server also lists this deployment's rooms (`${LIVEKIT_ROOM_NAME}-<uuid>`) and removes any identity it does not have in that call: at once if the server already removed it, otherwise on its second sighting. Each deployment that shares a LiveKit project therefore needs its own `LIVEKIT_ROOM_NAME`. The client also gives a tile to any LiveKit participant the server has not listed (`useCallTiles.ts`), so nobody in a room is ever invisible while that happens.
- **Browser → LiveKit:** a voice channel still joins immediately: `call-join` returns `livekitUrl` and a token, and the client connects to LiveKit directly. A direct conversation does not. `call-join` on a DM is refused. The caller rings with `dm-call-start`; the token is minted for both people only after `dm-call-accept`, on the tab that started the call and the tab that accepted it. The API key and secret never leave the server. Camera and screen share are published separately (`web/src/features/calls/videoPublish.ts`). The camera captures at an ideal 1080p30 — the browser negotiates down when the webcam cannot — and simulcasts 30 fps layers (360p floor, 720p, then the full capture capped at 3 Mbps) with degradation set to keep resolution. Screen share stays a single layer at the selected preset: 1440p60 / 6 Mbps, 1440p30 / 5 Mbps, 1080p60 / 5 Mbps (the default), or 1080p30 / 4.5 Mbps. The 60 fps presets hint `motion` and keep frame rate; the 30 fps ones hint `text` and keep resolution. The share is captured by the app itself (`useScreenShare.ts`, `displayCapture.ts`) rather than through `setScreenShareEnabled`, because the SDK does not pass `windowAudio` to `getDisplayMedia`. It asks for `windowAudio: 'window'` (the audio of the app that owns a window) and `restrictOwnAudio` (system audio without the call), and publishes a window's or a screen's audio only when the track reports `restrictOwnAudio: true`; otherwise the audio is stopped before anything is published and the sharer is told why. Chrome can only isolate an app or exclude its own audio where the OS allows it (Windows 11, macOS 14.2+); on Windows 10 and Linux a window or screen falls back to the whole system mix, which would carry the other participants' voices, so those shares go out without audio. A tab's audio is always published. The room enables adaptive stream at the display's pixel density and dynacast, so a viewer receives the camera layer that fits the tile and the publisher stops sending layers nobody is watching.
- **Restarts:** media flows between the browsers and LiveKit, so a deploy does not cut it. The server keeps who is in which call in Postgres and restores it on boot, holding each connection for `CALL_RESTORE_GRACE_MS` (default 90 s) while its client reconnects under the same LiveKit identity. How that works, and the rules that keep it working, are in `AGENTS.md` ("Realtime compatibility and deploys").
- **Phones in the background:** Android freezes a page soon after the person switches apps, so its connection to the server stops answering. A connection that was in a call is held for `CALL_RECONNECT_GRACE_MS` (default 3 min, instead of the usual `RECONNECT_GRACE_MS` of 30 s) before it counts as leaving, so coming back within that window resumes the same call. Audio may still pause while the page is frozen; only a native app can keep it running. The call is also registered with the Media Session API (`features/calls/useCallMediaSession.ts`), so browsers that show media controls offer mute and hang up.
- **Configuration:** `LIVEKIT_URL`, `LIVEKIT_SERVER_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, `LIVEKIT_ROOM_NAME`, `LIVEKIT_TOKEN_TTL_SECONDS`, `CALL_RECONNECT_GRACE_MS`, `CALL_RESTORE_GRACE_MS`. `LIVEKIT_URL` is also what the Content-Security-Policy lets the browser connect to (over ws and http; any `*.livekit.cloud` host for LiveKit Cloud), so it must be the URL clients really use. `LIVEKIT_SERVER_URL` (optional, defaults to `LIVEKIT_URL`) is where the server calls LiveKit's API (`RoomServiceClient`) when it reaches LiveKit by another address, as in the full stack of `docker-compose.yml`, where it is `http://livekit:7880` on the compose network while browsers use `ws://localhost:7880`. Tokens are not tied to either URL.
- **When missing:** the server boots and logs `LiveKit is not configured`; calls, camera and screen sharing fail.

## Resend

Transactional email. Used for one-time 6-digit codes (password recovery, email changes including linking an address to an older account that has none, turning on two-step login, the second step of a login when the account has two-step login on, and, with two-step login on, confirming the changes that could take the account's email away as its second factor) and for notices: the new sign-in alert, the email-changed notice, the account deletion notices and the data export link.

- **Code:** [`server/src/modules/auth/email.ts`](../server/src/modules/auth/email.ts) — one `POST https://api.resend.com/emails` with a bearer token. The text is localized to the account's language. Codes are issued and checked in `server/src/modules/auth/codes.ts` (only their sha256 is stored): recovery, email-change and setup codes last 30 minutes (requesting an email-change code, which is also how an account without an email links its first address, also needs the account's current password, like turning two-step login on or off and turning sign-in alerts off, so a stolen session alone cannot redirect recovery to another address), a login code 10 minutes, and each allows 5 tries. Wrong codes also count against the account (and, for password reset, the address) in the Postgres attempt counters (`ratelimit.ts`), so resending does not buy more guesses; code emails themselves are capped at 5 per 15 minutes per account and purpose.
- **New sign-in alert:** `sendLoginAlertEmail` in the same file, triggered by `noticeLogin` in [`server/src/modules/auth/loginAlert.ts`](../server/src/modules/auth/loginAlert.ts) after a password login or the second step of a two-step login creates a session (registration never alerts; it only records its browser). It names the browser and system (same parsing as the session list, copied to `modules/auth/describeUserAgent.ts` and pinned to the web copy by a test), the IP address, the approximate time in UTC and a link to Settings → Security → Active sessions, in the account's language. A browser is its address plus what its user agent says it is (browser, system, phone or desktop; the whole string only when nothing in it is recognised), so a browser updating itself does not read as new; one seen in the last 30 days (`known_logins`, kept apart from `sessions` because logging out deletes the session) does not alert, so ordinary re-logins stay quiet. Two logins of the same new browser at once send one alert. It is sent in the background and a failure is only logged, so it never fails a login. Only when delivery is configured, the account has an email and the account's switch (Settings → Security, on by default, `users.login_alert_email`) is on; at most 5 per hour per account.
- **Changes confirmed by the current email:** with two-step login on, the account's email is its second factor, so a stolen session plus the password is not enough to take it away. After the password, these send a code to the *current* address and wait for it: deleting the account (`account_deletion`), turning two-step login off (`two_factor_disable`), turning sign-in alerts off (`login_alert_disable`) and changing the email (`email_change_current`, whose confirmation is what sends the `email_change` code to the new address; asking again while that code is live resends it rather than starting over). A code of one purpose never confirms another. While email is down, such an account cannot make these changes (503 `email_unavailable`).
- **Email changed:** `sendEmailChangedEmail` goes to the old address once a change is confirmed, naming the new one masked, and the change signs out every other session of the account. Only when delivery is configured; a failure is only logged.
- **Account deletion:** `sendAccountDeletionScheduledEmail` goes out when a person asks to delete their account (the date it will happen and that signing in before then cancels it), from `scheduleAccountDeletion` in [`server/src/modules/auth/accountDeletion.ts`](../server/src/modules/auth/accountDeletion.ts); `sendAccountDeletedEmail` goes out once the deletion sweep has removed the account. Both only when delivery is configured and the account has an email, and a failure is only logged: the deletion goes ahead either way. With two-step login on, asking for the deletion also needs an `account_deletion` code (see above).
- **Data export:** `sendDataExportReadyEmail`, from the export job in [`server/src/modules/data-export/dataExport.ts`](../server/src/modules/data-export/dataExport.ts), sends the link to a finished export (`APP_URL` + `/api/account/data-export/<id>/download`, which only the signed-in account can open) and when it expires. Skipped without delivery, an account email or `APP_URL`; the export is still downloadable from Settings → Data & privacy, and a failed send is only logged.
- **Data sent:** the recipient address, the code, the username and `APP_URL`; for the sign-in alert, also the browser and system, the IP address and the time; for the email-changed notice, the new address masked; for the deletion notices, the date of the deletion; for the export, its link and expiry.
- **Configuration:** `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `APP_URL`. `RESEND_API_URL` (default `https://api.resend.com`) points at a local mail sink instead in development (`http://localhost:8025`, optional), in the full stack of `docker-compose.yml` and in the end-to-end stack; the sink prints or keeps the emails and sends nothing.
- **When missing:** requesting a code fails with `email_not_configured`, and two-step login cannot be turned on (Settings → Security explains why); sign-in alerts are skipped silently, and their switch is disabled with the reason. An older account that has no email stays on the "link your email" screen, since an address is only stored once its code is confirmed. If Resend rejects the send, the request fails with a 503 `email_delivery_failed`.
- **Two-step login depends on it:** an account that already has two-step login on cannot finish a login while email is down or unconfigured (the login answers 503 `email_unavailable`; the code step is never skipped). Removing the `RESEND_*` variables therefore locks those accounts out until they are restored.

## Web Push

Browser push notifications, delivered through each browser vendor's push service using the standard Web Push protocol with VAPID authentication.

- **Code:** [`server/src/modules/notifications/webPush.ts`](../server/src/modules/notifications/webPush.ts) (`web-push` library) and `web/src/shared/pushNotifications.ts` (service worker and `pushManager` subscription).
- **Destinations:** the subscription endpoint comes from the browser through an authenticated API, so it is validated before the server makes any outbound request. Only HTTPS endpoints without a custom port or credentials on these hosts are accepted: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.push.apple.com` and `*.notify.windows.com`. Keys must also have the exact lengths a real subscription has.
- **Content:** the title and body are built from the recipient's `users.locale` (`pushNotices.ts`; texts in `localeText.ts`) and never repeat the app name, which the OS already shows. A DM names the sender once, in the title; a channel message is titled `#channel · Server` with `Name: text` as the body; a mention (of a name, a role, `@everyone` or `@here`) says who, where and what (`Ana in #general · Server`, or `Ana mentioned you` in a DM), with role mentions written as `@Role`; friend requests and acceptances name the person; a server invitation is titled with the server and names the inviter. Message text is cut to 120 characters. An account can turn off "Show message text" (`users.push_show_content`, `GET`/`PATCH /api/notifications/push/preferences`): the server then leaves the text out, so a DM reads `Sent a message` and a channel message `Ana sent a message`, and a mention keeps its title with an empty body. Everything else stays the same.
- **Bursts:** every chat message in a conversation shares the tag `chat-<conversation>`, so a new one replaces the one on screen. The payload carries `renotify: true` so each still alerts; the browser shows only the latest text.
- **Sender avatar:** the payload adds `avatar` (an own `/uploads/<id>` path, the still frame of an animated avatar when there is one) next to the app `icon`. Uploads need the session cookie, so `web/public/sw.js` fetches the image itself and inlines it as the notification icon (2.5 s timeout, 300 KB cap), falling back to the app icon on any failure. External avatar URLs are never used. The iOS declarative format ignores `avatar` and `renotify` and always shows the app icon.
- **Delivery:** payloads use `aes128gcm`; the TTL is one hour for chat messages and 24 hours for everything else. Delivery honors the service's `Retry-After` and is driven by the notification outbox worker.
- **Configuration:** `PUSH_VAPID_PUBLIC_KEY`, `PUSH_VAPID_PRIVATE_KEY` and `PUSH_VAPID_SUBJECT`. They must be set **together** — setting only some makes the server refuse to start. Generate them with `npx web-push generate-vapid-keys`. In production `APP_URL` must use HTTPS.
- **Do not disturb:** a recipient whose `users.presence_status` is `dnd` at delivery time gets no push (`recipientAcceptsPush` in `notificationsPolicy.ts`). The event is marked processed, not postponed: the notification stays in the in-app list, and nothing piles up for the moment the status changes back.
- **Per server, channel and DM settings:** each account picks a level per server and per text channel or DM (All messages, Only mentions, Nothing) and can mute any of them for 15 min, 1 h, 8 h, 24 h or until turned back on (`notification_settings`, `GET /api/notification-settings`, `PATCH /api/notification-settings/{servers|conversations}/:id` with `level` and/or `mute`). At delivery the worker resolves the rule in `notificationSettingsPolicy.ts`: a channel's level wins over its server's, which wins over All; a muted server or a muted channel/DM sends nothing, mentions included. A message push needs All; a mention push needs All or Only mentions. As with do not disturb, a skipped push is marked processed, and the mention itself stays in the in-app list.
- **When missing:** push is simply unavailable (`pushAvailable` is false) and nothing is sent.

## KLIPY

GIF search and trending in the message composer.

- **Code:** [`web/src/features/gifs/klipy.ts`](../web/src/features/gifs/klipy.ts) calls `https://api.klipy.com/api/v1`; the server side is [`server/src/modules/gifs/gifs.ts`](../server/src/modules/gifs/gifs.ts).
- **Browser only, on purpose:** KLIPY's terms require requests and media loads to come from the user's own client. The server therefore does not proxy anything, GIFs included (they stay out of the [media proxy](#media-proxy)); `GET /api/gifs/config` hands the key to signed-in users (`Cache-Control: no-store`) so it stays out of the bundle and the repository.
- **Data sent:** KLIPY keys its "recent GIFs" and analytics by a customer ID. We send `sha256("klipy:" + userId)` truncated to 32 characters — stable per user, but not our real account ID.
- **Configuration:** `KLIPY_API_KEY`. When it is set, the Content-Security-Policy lets the browser connect to `https://api.klipy.com`; the GIFs themselves load from `static*.klipy.com` under the policy's general `https:` image and media sources.
- **When missing:** the config endpoint reports `enabled: false` and the GIF button is hidden.

## MyAnimeList

The "Recent anime activity" widget on a user's Wall.

- **Code:** [`server/src/integrations/myanimelist/myanimelist.ts`](../server/src/integrations/myanimelist/myanimelist.ts).
- **API:** the official v2 API, `GET https://api.myanimelist.net/v2/users/{username}/animelist` sorted by `list_updated_at`, limited to 8 entries, with the `X-MAL-CLIENT-ID` header. Public lists need only an application client ID, not a user login. Cover images are accepted only from `cdn.myanimelist.net`; the browser loads them through the [media proxy](#media-proxy), so the CDN sees the server, not the viewer.
- **Limits of the API:** it has no favorites or characters endpoint, so recent activity is the only MyAnimeList widget.
- **Configuration:** register an app at <https://myanimelist.net/apiconfig> and set `MAL_CLIENT_ID`.
- **When missing:** MyAnimeList connections report `unavailable` and retry with backoff; the rest of the app is unaffected.
- **Data sent:** the username the account owner typed (self-declared, ownership is not verified).

## GitHub

The "GitHub profile" and "Contributions" widgets.

- **Code:** [`server/src/integrations/github/github.ts`](../server/src/integrations/github/github.ts).
- **Requests per sync:** two, both unauthenticated and sent with `User-Agent: Linkord`.
  1. `GET https://api.github.com/users/{username}` (REST, API version `2022-11-28`) for name, avatar and counts. Avatars are accepted only from `avatars.githubusercontent.com` and reach the browser through the [media proxy](#media-proxy).
  2. `GET https://github.com/users/{username}/contributions`, the public contribution calendar. This is **HTML, not a versioned API**, so a markup change on GitHub can break parsing. The parser validates strictly (365–371 consecutive days, valid dates and levels); anything unrecognized fails the sync and keeps the previous snapshot.
- **Rate limit:** anonymous REST access allows 60 requests per hour per IP, so PostgreSQL coordinates one GitHub sync every 65 seconds across all server instances, and a rate-limit response postpones the whole provider until its cooldown ends. Other traffic from the same outbound IP reduces the budget.
- **Configuration:** none — no token, OAuth app or cookies.

### How connection syncing works (MyAnimeList and GitHub)

Both providers share one background worker ([`server/src/modules/connections/syncWorker.ts`](../server/src/modules/connections/syncWorker.ts)); viewing a profile only reads stored snapshots and never contacts the providers.

- The worker starts with the API process and checks for due connections every minute. It claims rows with a lease, so several instances never sync the same connection, and discards results if the connection was edited or deleted while the request was in flight.
- Each connection is refreshed every 24 hours. MyAnimeList requests are spaced at least 1.1 seconds apart through a shared PostgreSQL limiter.
- A failed sync keeps the last complete snapshot. `not_found`, `private` and `invalid_response` wait for the next daily cycle; `rate_limited` and `unavailable` retry with exponential backoff (honoring `Retry-After` and `X-RateLimit-Reset`).
- HTTP helper ([`server/src/integrations/connectionHttp.ts`](../server/src/integrations/connectionHttp.ts)): 10-second timeout, redirects are an error, response bodies are capped at 2 MB, and status codes map to the errors above (404 → `not_found`, 403 → `private` or `rate_limited`, 429 → `rate_limited`).
- Connections are managed under Settings → Connections; the owner chooses which widgets appear on the Wall. The games widgets are the exception: they need no connection (see [IGDB](#igdb)). See "Profile connections and Wall" in [DEVELOPMENT.md](DEVELOPMENT.md#profile-connections-and-wall).

## IGDB

Game search behind the four games widgets of the Wall (favorite game, games I like, games in rotation, want to play). Unlike MyAnimeList and GitHub there is **no connected account and no background sync**: the owner picks games by hand, and the server calls IGDB only while someone is searching.

- **Code:** [`server/src/integrations/igdb/igdb.ts`](../server/src/integrations/igdb/igdb.ts) (client and token), [`server/src/modules/games/`](../server/src/modules/games) (search, limits, saved lists). The picker is `web/src/features/games/`.
- **Auth:** IGDB signs in as a Twitch app. `POST https://id.twitch.tv/oauth2/token` with `grant_type=client_credentials` returns a token, which the server keeps in memory until a minute before it expires and replaces once when a request comes back 401. Simultaneous searches share one token request.
- **Search:** `GET /api/games/search?q=` (signed-in users only) runs `POST https://api.igdb.com/v4/games` with `search "…"; fields name,slug,first_release_date,cover.image_id; where version_parent = null; limit 10;` (editions are left out). The query is escaped for Apicalypse. The browser never talks to IGDB and never sees the credentials.
- **Rate limit:** IGDB allows about 4 requests per second per Client ID and answers 429 beyond that. Protections, in order:
  1. The text is normalized (lowercase, collapsed spaces, 2 to 64 characters); a shorter or longer one is a 400 without any request.
  2. Results are cached per normalized query for 6 hours (500 entries, shared by everyone).
  3. Identical searches in flight share one request.
  4. Each user may start 20 searches per minute that miss the cache; cache hits and shared searches are free (`429 rate_limited` with `Retry-After`).
  5. A PostgreSQL-coordinated slot (the `igdb` row of `connection_sync_limits`, one request per 300 ms, so about 3.3 per second across all instances) paces the actual requests. A search waits up to 2 seconds for a slot, then answers 429 with `Retry-After`. When IGDB itself answers 429, the same row holds everybody back for its `Retry-After` (at least a second).
  The client adds a 400 ms debounce, a 2-character minimum, cancellation of the previous request, and an in-memory cache per normalized query.
- **Errors on the wire:** `503 games_unavailable` (no credentials), `502 games_search_failed` (IGDB failed, timed out or sent an unrecognizable payload), `429 rate_limited`, `400 invalid_request`. Failures are never cached.
- **What is stored:** when a game is picked, the client sends back its snapshot (`igdbId`, name, slug, cover `image_id`, release year) and the server saves it in `profile_games`; viewing a profile never calls IGDB. The snapshot comes from the browser, so it is validated strictly (sizes, character sets, no duplicates, list limits) and the server builds the links itself: game pages on `www.igdb.com`, and covers as `/api/media-proxy/igdb/<size>/<image_id>` (`cover_small` in search, `cover_big` on the Wall), which the [media proxy](#media-proxy) fetches from `images.igdb.com`. A person can only misname their own picks. Snapshots are not refreshed afterwards.
- **Limits:** one favorite; eight games in each of the other lists.
- **Configuration:** register an app at <https://dev.twitch.tv/console> (the Twitch account needs two-factor authentication; the OAuth redirect URL is not used, `http://localhost` works) and set `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET`.
- **When missing:** if either is empty, searching answers `games_unavailable` and the picker says so; the widgets stay available and games already saved still show. The server boots normally.
- **Data sent:** only the search text typed (normalized) goes to IGDB, together with the app's credentials; nothing identifies the user. Covers are fetched by the server too, so IGDB never sees a viewer's IP.
- **Terms:** IGDB is free for non-commercial use under the Twitch Developer Service Agreement; commercial use needs a partnership with IGDB. Each game cover on the Wall links to its page on igdb.com and the game picker credits IGDB as the source of the covers and data; the IGDB docs read so far ask for nothing more.

## Link previews

Cards (title, description, pictures, favicon) for links pasted in chat. Unlike the services above, the destination is **any website a user chooses**, which makes it a server-side request forgery (SSRF) risk and shapes the whole design.

- **Code:** [`server/src/modules/link-preview/`](../server/src/modules/link-preview/): `linkPreview.ts` (endpoint, cache, rate limit), `resolvers.ts` (the chain), `openGraph.ts`, `oembed.ts`, `htmlMeta.ts` (HTML parser and charset), `pageFetch.ts` (every outbound request), and [`server/src/net/safeRequest.ts`](../server/src/net/safeRequest.ts). The endpoint is `GET /api/link-preview?url=…` for signed-in users; a message's previews are also fetched once by the server after it is sent and stored with it (`server/src/modules/messages/messageEmbeds.ts`).
- **Resolvers:** a URL goes through an ordered chain, each resolver with `matches`, an optional `transform` (the one form of a URL that has many) and `resolve`. The first preview with content wins; a resolver that fails or finds nothing hands over to the next. Today: [oEmbed](#oembed) for a fixed list of providers, then Open Graph for everything.
- **Open Graph:** the page is read with a real HTML parser (`htmlparser2`), only its `<head>`, ignoring `script`, `style`, `noscript`, `template` and `svg`. Title: `og:title` → `twitter:title` → `<title>`. Description: `og:description` → `description` → `twitter:description`. Pictures: every `og:image`, `og:image:url`, `og:image:secure_url`, `twitter:image` and `twitter:image:src`, deduplicated (an http/https twin counts once), at most 10; `image` is the first. Also `og:image:alt`, `og:site_name`, `theme-color`, `og:video`, `og:audio`, `og:type`, `twitter:card` and `twitter:player`.
- **Charset:** a byte order mark, then the `Content-Type` charset, then the page's `<meta charset>` or `http-equiv` in its first 1024 bytes, then UTF-8 (Node's `TextDecoder`, so latin-1/windows-1252 pages read right).
- **Type:** each preview says what it is: `twitter:card=photo` → `image`; `twitter:card=player` or `og:type=video.*` → `video` only when the player page is on the **player allowlist** (YouTube, youtube-nocookie, youtu.be, Vimeo, SoundCloud, Twitch, Streamable, X/Twitter, https only), kept in `player`; an `og:video` or `og:audio` elsewhere counts only when a request for it answers with a `video/*` or `audio/*` content type (headers only, the body is not downloaded), kept in `video`/`audio`; `summary_large_image` → `article`; anything else `link`. A link that is itself a picture, video or audio file becomes `image`, `video` or `audio`.
- **Safeguards:** every outbound request goes through `safeRequest`, which validates the resolved IP **at connection time** (so DNS rebinding cannot swap in a private address) against the private and special-purpose IPv4 and IPv6 ranges in [`ssrfGuard.ts`](../server/src/net/ssrfGuard.ts) (an IPv6 address that carries an IPv4 one, such as NAT64 `64:ff9b::/96` or 6to4, is judged by that IPv4 address), follows at most 3 redirects and revalidates each hop, times out after 5 seconds, and reads at most 1.5 MB of the page (stopping at `</head>`).
- **Probes:** the server reads the first bytes of the first picture (up to 256 KB, 3-second timeout) to learn its dimensions so the client can reserve space, and the headers of an `og:video`/`og:audio` (3-second timeout).
- **Cost controls:** results are cached in memory (500 entries, shared by everyone) under a canonical URL (YouTube's one form; `utm_*`, `fbclid`, `gclid` and similar tracking parameters and the fragment removed). A preview with content is kept 6 hours; a failed or empty one only 60 seconds, so a site that was briefly down gets its card on the next try. Each user may trigger 20 *new* fetches per minute; cache hits are free. A message gets at most 5 previews (its first 5 distinct links outside code and `<…>`).
- **Failures:** a preview whose fetch failed is not stored with its message, so the next read of that conversation fetches it again; meanwhile the endpoint answers the domain-only card.
- **Stored shape:** fields added since the first version (`type`, `images`, `imageAlt`, `audio`, `player`, `authorName`, `authorUrl`) are optional, because messages stored before them lack them and older tabs ignore them.
- **Pictures:** the preview's pictures and favicon are stored as the site gave them and sent to browsers as signed [media proxy](#media-proxy) addresses, so they load on networks that block the site and over plain http on an https page.
- **Privacy:** the target site sees the server's IP address, not the user's, for the page and for its pictures.
- **Direct image links:** a pasted link to a picture gets a preview too, whose image is the picture itself (any `image/*` answer, SVG and icons included, with the size read for raster formats). The chat draws that picture only from the preview's proxied address, never from the link; while the preview is missing it shows nothing, and when the server has no picture for the link it shows the "open link" fallback. The Media tab gets the same signed address with each image link (`imageUrl`).
- **Direct video and audio links** are not proxied (that would be a streaming proxy). Their player, and a page's `og:video`, is loaded from the link's own host only after the reader clicks "Load video from …", which says that host will see their IP address.
- **Embeddable links:** URL classification (YouTube, Twitch, direct media) is mirrored in `server/src/modules/link-preview/embeds.ts` and `web/src/shared/lib/chatEmbeds.ts`; change one, change both.

### oEmbed

For a fixed list of providers the server asks the provider's oEmbed endpoint instead of reading the page: their pages render in the browser (X, TikTok) or are very large (YouTube), while the oEmbed answer is a small JSON document.

| Provider | Links | Endpoint | Extra parameters |
| --- | --- | --- | --- |
| YouTube | video links in any form (`watch`, `youtu.be`, `shorts`, `embed`, `live`, nocookie), canonicalised to `youtube.com/watch?v=…&t=…` | `https://www.youtube.com/oembed` | `format=json` |
| Vimeo | any `vimeo.com` link | `https://vimeo.com/api/oembed.json` | |
| SoundCloud | any `soundcloud.com` link | `https://soundcloud.com/oembed` | `format=json` |
| Spotify | any `spotify.com` link | `https://open.spotify.com/oembed` | |
| X | `x.com`/`twitter.com` `…/status/<id>` | `https://publish.x.com/oembed` | `dnt=true` (no personalisation), `omit_script=true` (no `widgets.js`) |
| TikTok | `…/video/<id>` | `https://www.tiktok.com/oembed` | |
| Reddit | `…/comments/…` | `https://www.reddit.com/oembed` | |

- **Sent:** the link (`url=`) and the parameters above, through `safeRequest`, from the server's IP. No credentials; the answer is capped at 64 KB and 6 seconds.
- **Kept:** only structured fields: `title`, `description` (as plain text: SoundCloud puts markup in it), `author_name`/`author_url`, `provider_name`, `thumbnail_url` and its size (or `url` and size for a `photo`). The provider's `html` is **never stored or rendered**: for X and Reddit the plain text of its first paragraph becomes the description, and an `<iframe>` in it is kept as `player` only when its host is on the player allowlist.
- **Failure:** an endpoint that errors, times out, answers something too large or with nothing usable hands the link over to Open Graph. Endpoints a page advertises itself (`<link type="application/json+oembed">`) are not used.

## Embedded players

Pasted YouTube and Twitch links render as inline players. These are loaded **by the user's browser** from the providers' own domains; the server only classifies the URL.

- **Code:** [`web/src/features/media/GenericEmbed.tsx`](../web/src/features/media/GenericEmbed.tsx).
- **YouTube:** a click-to-play thumbnail (the preview image, falling back to `i.ytimg.com`'s `hqdefault.jpg` through `/api/media-proxy/youtube/<video id>`) that becomes a plain `www.youtube.com/embed` iframe, starting at the link's `t`/`start` time. YouTube's script API is not used: it would have to run in our page, which the Content-Security-Policy does not allow.
- **Twitch:** channel, VOD and clip embeds from `player.twitch.tv` and `clips.twitch.tv`, passing the current hostname as the required `parent` parameter.
- The players themselves always come from YouTube's and Twitch's own domains, so they do not play where those are blocked; only the thumbnails go through the [media proxy](#media-proxy).
- No credentials are involved.

## Media proxy

Serves the third-party pictures above from our own domain, `GET /api/media-proxy/...` (signed-in users only), so covers, avatars and previews show on networks that block those services, and the services never see who is looking.

- **Code:** [`server/src/modules/media-proxy/`](../server/src/modules/media-proxy): `mediaProxyUrls.ts` (addresses and allowlist), `mediaProxy.ts` (fetch, cache, limits, routes), `mediaProxyKey.ts` (signing key). The client builds only the two id-based addresses, in `web/src/shared/lib/mediaProxy.ts`.
- **Never an open proxy.** A picture is named either by an id on a fixed host, or by a URL the server already holds, signed with HMAC-SHA256:
  - `/api/media-proxy/igdb/<cover_small|cover_big>/<image_id>` → `images.igdb.com`
  - `/api/media-proxy/youtube/<video id>` → `i.ytimg.com/vi/<id>/hqdefault.jpg`
  - `/api/media-proxy/<mal|github|preview>/<signature>?u=<base64url URL>`, built by the server when it sends a Wall, a link preview or a Media tab page. `mal` only reaches `https://cdn.myanimelist.net`, `github` only `https://avatars.githubusercontent.com`, and `preview` any public http(s) host (the pictures the link preview found). Anything else is a 404 without a request.
  - Stored data keeps the original URLs; they are rewritten as they are sent, so stored messages and snapshots do not depend on the key or on the proxy being on.
- **Signing key:** made on first boot and kept in the `instance_secrets` table, so an address a tab already holds still opens after a deploy. Nothing to configure.
- **Safeguards:** every request goes through `net/safeRequest.ts` (IP checked at connection time). No redirects on the fixed hosts, at most 3 for previews. 8-second timeout for the whole download. 5 MB cap (a larger `Content-Length` is refused before reading). The upstream must say `image/*` **and** the bytes must be JPEG, PNG, GIF, WebP, AVIF or ICO; the response's type comes from the bytes. An SVG is never passed on, since it is a document that could run script on our origin: it is drawn into a PNG of at most 512 px with sharp (1 MB and 3-second limits), and librsvg, given bytes with no base path, loads nothing the SVG references.
- **Cache:** in memory, by upstream URL, up to 64 MB (least recently used dropped first), each picture for up to 7 days. A failure (a missing favicon, a removed cover) is remembered for 30 minutes. Simultaneous requests for one picture share one fetch. Browsers get `Cache-Control: private, max-age=604800`, an `ETag` of the content (`If-None-Match` answers 304), `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: same-origin`.
- **Rate limits:** only fetches that miss the cache count: 120 per minute per account and 1200 per minute for the whole server (`429 rate_limited` with `Retry-After`).
- **Errors on the wire:** `404 not_found` (unknown or tampered address), `401 unauthenticated`, `415 not_an_image`, `413 image_too_large`, `502 image_unavailable` (upstream failed, timed out or the address is private), `429 rate_limited`.
- **Cost:** each picture is downloaded once per cache lifetime (a restart empties the cache) and then served from memory, so bandwidth grows with the number of distinct pictures and of viewers whose browser does not have them yet; memory stays under the 64 MB budget.
- **Configuration:** `MEDIA_PROXY=0` switches the fetching off to save bandwidth: the same addresses then answer `302` to the service itself, so pictures load as before the proxy (and again depend on the viewer's network, and hand the viewer's IP to each host). The policy's `img-src` then allows any `https:` host again, for those redirects.
- **Not covered:** GIFs (KLIPY's terms) load from `*.klipy.com`, and direct video and audio links from their own host after a click (see [link previews](#link-previews)). Webhook embeds carry no pictures, and images in a Markdown attachment preview show as links unless they are on our own origin. The Content-Security-Policy's `img-src` allows only our origin and `https://*.klipy.com` while the proxy is on.

## Adding a new integration

1. **Decide who makes the call.** Prefer the server for anything with a secret or a rate limit. Call from the browser only when the provider's terms require it (as with KLIPY) — and then serve the key through an authenticated endpoint, never the bundle.
2. **Put it in the right place.** Server-side adapters live in `server/src/integrations/<name>/`; domain logic that uses them stays in `server/src/modules/<domain>/`. Frontend-only integrations live inside their feature folder.
3. **Make the credential optional.** Read it in `server/src/config/env.ts`, document it in `.env.example`, and degrade quietly when it is empty (hide the feature or report `unavailable`) rather than crashing the server. Variables that only work together, like the VAPID trio, should fail fast when partly set.
4. **Never trust the destination.** If any part of the URL comes from a user, use `net/safeRequest.ts`. Validate hosts for images and endpoints you accept from a response, and cap time and body size.
5. **Respect rate limits.** For background work, reuse the connection-sync queue and its PostgreSQL-coordinated limits instead of calling providers per profile view; map provider status codes to the shared error codes.
6. **Preserve good data.** A failed or malformed response must never replace a previously valid snapshot.
7. **Test with injected requests.** Adapters take their `request` function as a parameter so tests never hit the network; follow the pattern in `server/tests/integrations/`.
8. **Allow it in the Content-Security-Policy** if the browser talks to it: add the host to `server/src/http/securityHeaders.ts` (see "Content-Security-Policy" in [DEVELOPMENT.md](DEVELOPMENT.md#content-security-policy)). The browser never loads a provider's script into our page.
9. **Document it here:** the table above, the data that leaves our system, and what happens when the credential is missing.
